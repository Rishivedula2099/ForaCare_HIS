## 1. Executive Summary

This document captures all operational, infrastructural, clinical, and integration assumptions made during Phase 0 planning. Each assumption has an assigned owner, validation criteria, and a mitigation path should the assumption prove false.

---

## 2. Assumptions Register

| Assumption ID | Domain | Assumption Description | Impact if Invalid | Validation Criteria / Verification Method | Owner | Status |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| `ASM-INF-01` | Infrastructure | Local hospital deployment will use a dedicated PC/Server running Windows 10/11 or Windows Server with minimum 16GB RAM and virtualization/WSL2 enabled for Docker. | Docker container engine cannot boot; would require native Windows binaries or external cloud hosting. | Pre-installation audit script verifies OS version, RAM, and Docker Desktop status. | Dev 1 | VALIDATED |
| `ASM-INF-02` | Network | Local hospital PCs (Reception, Doctor OPD, Nursing Station, Lab, Cashier) are connected on a high-speed Local Area Network (LAN) and can reach the local server IP on ports `80`/`3000` and `8000`. | Workstations cannot load web app or submit transactions. | Network ping and HTTP health check verification during facility setup. | Hospital IT / Dev 1 | VALIDATED |
| `ASM-OPS-01` | Operations | A pilot hospital will be configured as a single initial tenant (`tenant_id`) with one primary facility (`facility_id`), even though the database schema strictly supports multi-tenancy. | Multi-hospital data isolation would need manual partitioning. | Database schema incorporates `tenant_id` and `facility_id` from initial migration. | Dev 1 | VALIDATED |
| `ASM-OPS-02` | Operations | Hospital users (receptionists, nurses, doctors, lab techs) will operate the application via modern Chromium-based desktop browsers (Google Chrome, Microsoft Edge). | Cross-browser compatibility issues on legacy browsers (e.g. IE11). | Enforce browser version check in web application shell. | Dev 2 | VALIDATED |
| `ASM-HW-01` | Hardware | Front desk and pharmacy thermal slip printers will be installed as standard Windows printers via official OEM drivers. | Direct USB/network ESC/POS socket printing would need custom client side agent. | Browser print dialog can target the printer with 80mm paper width profile. | Dev 2 | VALIDATED |
| `ASM-HW-02` | Hardware | Lab barcode scanners are standard USB HID (keyboard wedge) devices that input scanned alphanumeric strings directly into active inputs followed by an Enter key event. | Would require proprietary scanner driver or WebUSB API integration. | Standard barcode scanner tested against text input field. | Dev 2 | VALIDATED |
| `ASM-CLI-01` | Clinical | Clinical consultations in Phase 1 MVP do not require full standardized SNOMED-CT or ICD-11 ontology coding; free-text diagnosis and search-assisted common symptom dictionaries are sufficient. | High complexity in clinical consultation screens and doctor resistance to adoption. | Doctor sign-off on simple diagnosis entry in UAT. | Hospital Admin / Doctor Lead | VALIDATED |
| `ASM-CLI-02` | Clinical | Doctor electronic signature on prescriptions and lab reports will be represented as an approved digital stamp / cryptographic signature block generated by the system, rather than an external PKI smartcard hardware token. | External PKI USB cryptographic token integration required. | Medical superintendent sign-off on digital approval block. | Hospital Admin | TBD |
| `ASM-BIL-01` | Billing | Phase 1 MVP financial transactions will be recorded manually by cashiers (Cash, manual UPI QR verification, external POS card swipe); payment gateway automated webhooks are optional Phase 2 enhancements. | Cashier cannot record payments if offline or if gateway down. | Cashier can close shift balance accurately with manual receipt reconciliation. | Dev 1 & Dev 2 | VALIDATED |
| `ASM-LAB-01` | Laboratory | Laboratory equipment and hematology/biochemistry analyzers will not be interfaced via ASTM/HL7 bidirectional serial/LAN protocols in Phase 1; lab techs will manually transcribe analyzer values into the LIS screen. | Manual data entry required by technicians; slight risk of transcription typo. | Lab manager approval of dual-entry or verification step by Pathologist before report sign-off. | Lab Lead / Hospital Admin | VALIDATED |
| `ASM-INT-01` | Integrations | ABDM/ABHA integration will be delivered as an adapter interface. Phase 1 will execute against a fully compliant local Mock Adapter; Sandbox/Production credentials will be plugged in Phase 8 without refactoring business logic. | Delivery blocked waiting for National Health Authority (NHA) credentials. | Mock adapter passes 100% of integration test suites for M1, M2, and M3 schemas. | Dev 1 | VALIDATED |
| `ASM-MIG-01` | Data Migration | Initial deployment is a greenfield deployment; no historical legacy database migration (SQL/Access/Excel dumps) is required for go-live, other than initial master catalog CSV uploads. | Complex ETL scripts needed for historical patient records. | Facility confirmation of greenfield go-live date. | Production Owner | TBD |

## 3. Assumption Invalidation & Escalation Path

Should any assumption above be invalidated:
1. **Notification:** The owner flags the item in the Weekly Phase Standup.
2. **Impact Assessment:** Dev 1 and Dev 2 evaluate timeline, architectural, and hardware impact.
3. **Escalation:** If the change expands MVP scope by more than 3 working days, it is formally deferred to Phase 2, or an architectural amendment is submitted to the Production Owner for sign-off.
